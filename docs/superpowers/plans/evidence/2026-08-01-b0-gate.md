## The three rulings

Step 1 (rendering the candidates in `apps/mobile` for the owner) was already
done before this task started. The owner ruled on 2026-08-03. What follows is
the record of each ruling as written into `packages/tokens/src/tokens.json`.

### `line` = `#D9DBD5`, opaque

> Owner ruled at a render, 2026-08-03: the document's value, #D9DBD5, opaque.
> Borders do not composite. This is the cheaper branch for React Native: one
> value, no per-surface pre-composited variants, and no compositing logic
> anywhere in the native module — a translucent line would have needed a
> hand-authored blend per surface it sits on (paper, white, ink-950), because
> React Native authors border colours opaque and has no custom properties to
> composite through.

The document (`docs/05-design-system.md:29`) and the shipped prototype
(`packages/ui/src/tokens.css:23`, now deleted) disagreed in *kind*, not just
value: `#D9DBD5` opaque versus `rgba(72, 76, 94, .17)`. That is not a
question a measurement or a "rendered beats written" rule can settle — a
17%-alpha grey over `paper`, `white` and `ink-950` produces three different
effective colours, and React Native has no mechanism to composite a
translucent border colour against whatever surface it happens to sit on. The
owner's ruling picks the opaque value, which is also the cheaper one to
implement: `color["line"]` is a single value everywhere, with nothing to
pre-compute per surface and no compositing logic to write, test, or keep in
sync as new surfaces are added.

### `shadow` = `0 8px 30px rgba(21,23,25,.07)`, one token, not a ladder

> Owner ruled at a render, 2026-08-03: the document's single shadow, 0 8px
> 30px rgba(21,23,25,.07) — not the shipped six-step ladder
> (packages/ui/src/tokens.css:33-36,42-43). The document defines one shadow,
> so the source carries one shadow token, named `shadow` to match the
> document's own naming, which has no scale suffix. No further elevation
> steps are invented around it: a token with no consumer is an untested
> assertion, and B0's single screen (apps/mobile/src/screens/token-proof.tsx)
> uses no shadow at all — further steps arrive in B1 when a screen needs
> them. androidElevation is hand-authored at 3, because Android's elevation
> encodes offset, blur and opacity in one scalar and cannot be derived from
> the CSS value: a shallow shadow with an 8px offset and 7% opacity reads as a
> resting card lifted slightly off its surface, not a floating dialog, so it
> sits near Material's default resting-card elevation (~3dp) — well under a
> dialog's 24dp and above a flat element's 0-1dp.

The shipped ladder (`--shadow-xs`, `--shadow-sm`, `--shadow`, `--shadow-lime`,
plus `--atlas-shadow`, `--atlas-folio-shadow`) used a darker ink base
(`rgba(23,23,23,…)`) and ran from a 16px blur up to a 70px blur — the
document's own words call for "shallow", and 70px is not shallow by any
reading. A second implementer independently arrived at the document's exact
value at `apps/demo/src/styles/theme.css:215` (`--shadow-raised`'s sibling
comment quotes doc 05 directly: "borders carry most structure; shadows are
shallow"). The source now carries exactly the one shadow the document
defines, named `shadow` with no scale suffix, and nothing else — inventing a
ladder around a single documented value, or keeping the six shipped steps,
would both be assertions with no consumer to validate them.

**`androidElevation`.** I authored `3`. Reasoning: Android's `elevation`
prop is a single scalar that stands in for offset, blur *and* shadow opacity
all at once — there's no formula from `{offsetY: 8, blurRadius: 30, alpha:
0.07}` to an elevation number, so it has to be a judgment call recorded next
to the value it approximates, not computed by a generator. Material's own
elevation scale treats ~1dp as barely-there (resting button), ~3dp as a
resting card lifted slightly off the page, ~6-8dp as an actively-raised
element (FAB, app bar), and ~24dp as a modal floating well above the page.
An 8px offset with 7% opacity is a soft, close-to-the-surface shadow — it
reads as a card sitting a little proud of its background, not as anything
that needs to visually separate from the whole page the way a dialog does.
`3` is deliberately near the "resting card" end of that scale and nowhere
near the dialog end.

## The `rgba()` helper's first real consumer

`packages/tokens/scripts/generate-css.mjs`'s `rgba()` helper existed since
Task 1 but was unreachable — all ten original colours have `alpha: 1`, so the
`t.alpha === 1 ? t.hex : rgba(t)` branch never took the `rgba()` path. The
shadow's colour (`{ hex: "#151719", alpha: 0.07 }`) is the first value to
actually exercise it. Verified directly rather than assumed:

```
$ node -e '
function rgba({ hex, alpha }) {
  const n = parseInt(hex.slice(1), 16);
  return `rgba(${(n >> 16) & 255}, ${(n >> 8) & 255}, ${n & 255}, ${alpha})`;
}
console.log(rgba({hex:"#151719", alpha:0.07}));
'
rgba(21, 23, 25, 0.07)
```

`21, 23, 25` is exactly the document's `rgba(21,23,25,.07)`. The committed
`packages/ui/src/tokens.generated.css` shows the helper's real output:
`--shadow: 0px 8px 30px 0px rgba(21, 23, 25, 0.07);`.

## Finding: retiring the old stylesheet changes what `apps/landing` renders,
## beyond the three ruled tokens

The task's ambiguity-resolution instructions say explicitly: if retiring the
old file changes what `apps/landing` renders in any way beyond the three
ruled tokens, stop and report it rather than absorb it silently. It does.
Reported here rather than fixed, because fixing it is a design decision (what
replaces the lost typography rules, and by what mechanism) that is out of
this task's colour-and-shadow-only scope.

The old `tokens.css` carried three things that were never token values in the
`tokens.json` sense:

1. **A `body { font-family; color; background; font-synthesis }` rule.**
   `apps/landing/app/page.tsx` never sets its own font — it relies on this
   rule (via the old stylesheet) to apply `"Inter Variable", Inter,
   sans-serif` to the page and `font-synthesis: none`.
2. **An `h1, h2, h3, .brand, strong { font-family: "Manrope Variable" … }`
   rule.** `apps/landing/app/page.tsx:18` renders `<span className="brand">`
   specifically to pick this up.
3. **Custom-property names that don't match the source's.** The old file
   named the ink/signal/slate/red/amber/blue tokens `--ink`, `--signal`,
   `--slate`, `--red`, `--amber`, `--blue` (bare); the generated source names
   them `--ink-950`, `--signal-500`, `--slate-600`, `--red-500`, `--amber-500`
   and, per the owner's ruling, `--blue-500`. `apps/landing/app/page.tsx:14`
   sets `color: "var(--ink)"` inline — that custom property no longer exists
   at all in the generated file.

None of `tokens.json`'s design ever modeled "apply this custom property to
this selector" — the generator's whole contract is a flat `:root { --token:
value }` block, nothing more. So this loss was structural to the migration
described across Tasks 1-5, not a mistake introduced by this task's edits.

Confirmed against the real build output, not just by reading source. Before
this task, the compiled CSS for `apps/landing` (`apps/landing/.next` as it
stood at the start of this task) contained:

```css
:root{--ink:#171717;--ink-2:#242424;--paper:#fbfbfb;--white:#fff;--signal:#c6ff34;--signal-dark:#667f12;--slate:#484c5e;--line:#484c5e2b;--muted:#666979;--amber:#f2b84b;--red:#e45c55;--blue:#65719a;--glass:#ffffffc7; …}
body{color:var(--ink);background:var(--paper);font-synthesis:none;font-family:Inter Variable,Inter,sans-serif}
h1,h2,h3,.brand,strong{font-family:Manrope Variable,Manrope,sans-serif}
```

After this task's `pnpm build`, the compiled CSS for `apps/landing`
(`apps/landing/.next/static/chunks/09n7el0h9qqec.css`) is:

```css
:root{--ink-950:#171717;--ink-800:#242424;--paper:#fbfbfb;--white:#fff;--signal-500:#c6ff34;--slate-600:#484c5e;--signal-700:#667f12;--amber-500:#f2b84b;--red-500:#e45c55;--muted:#666979;--line:#d9dbd5;--blue-500:#3756a1;--shadow:0px 8px 30px 0px #15171912}
```

No `body {}` rule, no `.brand`/heading font-family rule, no `--ink` (or
`--signal`, `--slate`, `--red`, `--amber`, `--blue`) at all. `--paper` and
`--muted` are unaffected (same names, same values, so
`background: var(--paper)` and `color: var(--muted)` in `page.tsx` still
resolve exactly as before). `color: var(--ink)` in `page.tsx:14` now
resolves to nothing, so `<main>`'s text colour falls back to the browser's
inherited/initial value instead of `#171717` — visually similar on most
browsers' default black, but not the same mechanism, and not guaranteed.
Both the page body and the `.brand` span lose their font-family assignment
entirely and fall back to the browser's default font stack, even though
`@fontsource-variable/inter` and `@fontsource-variable/manrope` are still
imported in `apps/landing/app/layout.tsx` and still register the `@font-face`
rules — nothing in the new source applies them to anything.

This is not touched by this task, per its own colour-and-shadow-only scope:
`apps/landing/app/page.tsx` is not in Task 5's file list, and adding
typography tokens or a base-stylesheet mechanism to fix it would be exactly
the scope expansion the task's global constraints forbid. It is left as a
finding for whoever picks up `apps/landing`'s next slice.

## What this slice does not close

> The device-install step is NOT DONE. It is blocked on three accounts and two
> devices, and no code closes it.

Recorded in full in
[2026-08-01-b0-procurement.md](2026-08-01-b0-procurement.md): an Apple
Developer Program membership (which itself needs a D-U-N-S number from Dun &
Bradstreet first), a Google Play Console account, and a funded Expo/EAS
account, plus a physical supported iPhone and a physical lower-resource
Android device. `apps/mobile/eas.json` carries build profiles that have never
been resolved by any EAS command in this environment.

> The fidelity guard does not catch a wrong-but-consistent value. Once a value
> is in the source, generation makes it consistent everywhere — which is exactly
> how `muted` drifted with its name intact. Only the visual gate catches that
> class.

`packages/testing/src/token-fidelity.test.ts` asserts that generated output
matches `tokens.json` and that every documented token is accounted for. It
does not and cannot assert that a value is the *right* value — the three
rulings this task recorded were themselves not something any test could have
produced; they required an owner looking at a render.

> Five of seven token categories remain untokenised, by decision. They are
> tokenised in B1 when a screen consumes them.

Only colour and shadow are in `packages/tokens/src/tokens.json`. Typography,
spacing, radius, border-width and motion are not — the stated principle,
repeated throughout this slice's specs and this task's own instructions, is
that a token with no consumer is an untested assertion (the same principle
that kept this task from inventing an elevation ladder around the single
ruled shadow). They arrive in B1 when a screen actually needs them.
