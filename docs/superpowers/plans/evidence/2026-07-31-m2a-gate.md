The first pre-landing pass found thirteen; eleven are fixed. The second verified
those fixes — four held, five held only partly — and found eleven more. The
third verified those and found seven, of which six were real; all six are fixed
in `0031`.

The third pass is the one worth reading, because of what it says about the two
before it. Both had reported the upload state machine as closed. It was not: the
app role still held UPDATE on `status`, so every "server-only" transition was
one the caller could decline to use.

**`--force` matters in that table.** turbo's `test` task declared no `inputs`, so
its hash covered package sources only. Migrations live outside every package,
which meant a SQL-only change left every hash untouched and turbo replayed a
cached pass. Several "suite green" reports earlier in this session were replayed
logs rather than runs. The task now takes `supabase/migrations`, `seed.sql` and
`config.toml` as inputs, and the numbers above come from a forced run.

## What the review changed

The plan-stage review changed four things about the design: per-root valuation
lineage instead of a telescopic one (D1), one storage bucket with an immutable
key instead of a non-atomic promotion (D3), a dedicated purge queue instead of
the transaction outbox (D4), and magic-byte sniffing instead of re-reading the
client's MIME string (D7).

The pre-landing review found nine more defects and one design gap. The four
worth naming:

- **Money was destroyed by over-contract corrections.** A reduction shrank a
  root's allocation in proportion to its total quantity, including the
  over-contract part that never received money. With a contract quantity of 4
  and a pool of 400, a correction stranded 67 units permanently. Migration
  `0022` adds the funded-quantity fact the fix needs; it is not derivable after
  the fact, because each carve takes from the pool remaining at that moment.
- **Replaying an intent creation resurrected purged bytes.** The upload grant is
  minted outside the idempotency callback, which does not re-run, so a caller
  who had lost the capability or whose intent had been purged could replay and
  receive a working token.
- **Evidence was route-enforced only.** Any session with `evidence.record` could
  insert an `evidence_objects` row with a chosen hash, key, recorder and
  `inspection_status = 'passed'`. Migration `0023` binds every field to the
  intent it claims to come from.
- **Five problem codes were invented** while `technical/error-catalog.csv`
  already defined a code for each case. The mobile client would have had nothing
  to map them onto. Neither the review nor its outside voice caught this; a
  fidelity test now fails on any route emitting an uncatalogued code.
- **Evidence could be declared inspected by anyone who could write SQL.** The
  binding in `0023` fixed hash, key, size and recorder to the intent but not
  `inspection_status`, so a holder of `evidence.record` could authorize an
  intent, upload nothing, and insert a row claiming `passed`. Constraining more
  columns would not have fixed the shape: evidence is the product of one
  transition, so the insert grant is gone and `app.finalize_upload_intent` is
  the only way in (`0029`).
- **Blocking and the quota were member-writable or unserialized.** `blocked_at`
  was grantable, so an owner could postpone it and keep content out of the purge
  queue forever; the quota was read-then-reserve with nothing serializing it.
  Both are commands or locks now (`0028`, `0030`).
- **The state machine was never actually closed.** `0028` and `0029` each moved
  a transition behind a command and said so; the app role kept UPDATE on
  `status` throughout, so the creator of an intent could set `available` with no
  evidence behind it and release the reservation. `0031` revokes the grant
  entirely and adds the one missing command, so there is no longer any way to
  move an intent except through a transition that checks what the move is.
- **The quota gave storage back for bytes that were still there.** Usage counted
  by status rather than by whether the object had been deleted, so an expiring
  grant returned the room while the object stayed in the bucket. Upload, never
  finalize, wait, repeat. Two tests asserted this as intended behaviour, one of
  them in the words "an expired intent promises nothing, so the room comes
  back". Usage now counts every unpurged byte, and `purged_at` is the only thing
  that frees it.
- **Evidence could be written for bytes that did not exist.** Everything the
  finalization command verified was about the intent — the hash and size it had
  declared, the recorder, the key — so presenting those values produced a
  receipt naming a storage key where nothing had ever been uploaded. The route
  does read the object and hash it, which is the argument `0029` had already
  rejected for `inspection_status`. `0032` makes the command check the bucket.
  Every database-level test in the hardening suite had been finalizing against
  an empty bucket, which is how this survived them.
- **Retries published the same event once per retry.** Parallel finalizations
  produced one evidence row, which is what the concurrency test asserted, and
  each losing call still appended its own capture event, audit entry and
  `evidence.available` outbox row. The command now reports whether it created
  the evidence, and only the call that did emits anything.

## Two figures this slice had to pick

`technical/data-retention-catalog.csv` marks all 126 durations in the product
`duration_external_gate`, so neither is settled here.

- **Evidence quota** defaults to NULL, meaning unlimited — the behaviour that
  already shipped. Turning it on with an invented number would break workspaces
  to enforce a rule nobody approved. The mechanism is implemented and tested.
- **Blocked-content retention** defaults to **7 days**, matching the quarantine
  window `execution-and-evidence.md` already sets for a revoked pending
  original, and the single "Restricted quarantine" class
  `files-and-storage.md` puts blocked and orphaned bytes in. Nothing is lost by
  deleting them: a blocked upload never produces a receipt, so the capturing
  device still holds the original, and the diagnostic record on the intent
  survives the deletion.

Both are recorded in `TODOS.md` as awaiting the approved schedule.

## One reported risk that was checked and is not one

The third pass flagged that `0030`'s composite foreign key validates existing
rows on the spot, so any allocation admitted before it would block the migration
while the append-only trigger prevents ordinary repair, and asked for a preflight
query and a repair procedure.

There is no environment where that can happen. `valuation_allocations` is
created in `0015`, and `main` carries `0001`–`0014`; every migration from `0015`
on is unreleased and lands together. No deployed database has ever held a row in
that table. The one place it could bite is a developer's local database that
applied `0015`–`0029`, wrote allocations, then pulled this branch without
resetting — which `supabase db reset` handles and which the test suite requires
anyway. Writing a repair procedure for rows that cannot exist would be
ceremony, so this is recorded rather than built.

## Operations steps NOT performed

Recorded as outstanding rather than claimed as done:

- **The evidence purge worker is not scheduled.** `0021` schedules only the
  expiry marking, which is pure SQL. Deleting bytes needs storage credentials,
  so `apps/app/src/lib/evidence-purge.ts` has to be wired to a runtime that
  holds them. Until then INV-047's 24-hour guarantee is demonstrated by tests,
  not operating anywhere. Codex flagged this independently.
- **`pg_cron` scheduling is unverified outside local.** `0021` and M1's `0005`
  both guard on the extension and log a notice when it is absent.
- **No CI run.** CI triggers on push to main or on a pull request; this branch
  has neither.

## Known limitations, stated rather than implied

- **`inspection_status = 'passed'` means the magic bytes matched the declared
  type.** It is not a malware verdict. v0.1 ships no scanner, the spec says so,
  and the policy version is recorded on every evidence row so a future scanner's
  results are distinguishable.
- **`capture_events.event_source` is not enforceable.** The database cannot tell
  the server's assertion from a member's without a service principal;
  `service.upload_finalize` exists in the capability catalog and is the work
  that closes it.
- **Valuation funding is first-come and is not redistributed.** If one root
  takes the pool and later withdraws, a second root whose performed quantity is
  now within contract holds nothing. Closing it means a correction writing
  allocations for other roots, which is a lineage decision rather than a fix. It
  is a named test in `valuation.test.ts` and a P1 in `TODOS.md`.

## Testing posture

Every load-bearing guarantee was mutation-checked: the assertion was shown to
fail when the mechanism it claims to test is removed. That covers the valuation
reconciliation, the work-item lock, the INV-025 reserve guard, the INV-047
recheck, the intent state gate, the conditional promotion, the template version
race, the contract-version pin, and bucket privacy.

Every constraint added by the hardening migrations has an attack test that
attempts the exact write it exists to stop. That is how the `allowed_media`
check was caught accepting `{}`: `jsonb_typeof` returns NULL for an absent key,
and a CHECK evaluating to NULL passes.

Three tests had to be rewritten because they asserted the defect. One pinned the
UPDATE grant list to exactly the four state-machine columns — written to prove
the storage key was unwritable, which it does, and in doing so it blessed the
writable `status` beside it and stayed green through two migrations that claimed
those transitions were server-only. One asserted the quota returns storage when
a grant expires. One asserted a single evidence row under parallel finalization
and counted nothing downstream of it. A test that encodes the current behaviour
protects it; the question a test has to answer is whether that behaviour is
right.

Money fixtures span the tax mode × price state × valuation basis matrix, built
through the real import path rather than seeded, because `work_items` are
immutable and a seeded fixture would not prove the importer produces those
shapes. That choice surfaced a v0.1-M1 defect: publishing any estimate
containing a zero-priced row returned 500.

The lesson the session keeps repeating is narrower than "test more". Both money
defects survived a green suite because the fixtures never left the shape the
author had in mind — the first walk never crossed the contract quantity, and no
M1 fixture ever imported a zero price. The tests that found them were the ones
built to leave that shape deliberately.
