# GoProceed v0.1 — M0 through M6 — implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development
> (recommended) or superpowers:executing-plans to implement this plan task-by-task.
> Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the six steps ADR-006 decision 1 defines — the object, the phone,
the refusal, the act, the link, the money — on the seventeen tables v0.1 does not
have yet, without adding one capability that no numbered step needs, and without
carrying forward the three places where the running code still implements the
model ADR-005 decision 2 replaced.

**Architecture:** Seven milestones. M0 is documents, procedures and controls and
builds no table; it runs in parallel with M1–M5 and gates M6. M1 gives a contract
version a rule-version set and refuses to publish a baseline without one. M2
materialises the obligation set at assignment creation and gives the foreman a
browser page. M3 builds `can_close_stage` and makes the closure command refuse.
M4 assembles Додаток В from already-recorded facts only. M5 puts one requirement
occurrence behind one personal link. M6 is a single query over `blocked_reasons`
and `work_items`. Each milestone's schema lands as additive migrations from
`0041` upward; each milestone's refusals land as tests that assert the refusal
before the code that performs it exists.

**Tech Stack:** PostgreSQL 15 (Supabase), Node 24, pnpm 9 workspaces, Next.js App
Router (`apps/app`), Zod contracts (`@goproceed/contracts`), Vitest.

## Global constraints

- **Applied migrations are append-only history.** `0001`–`0040` are never edited,
  for any reason, including to fix a comment that is wrong. A correction to a
  comment in an applied migration lands in the migration that completes the work
  the comment describes. The next free number is **`0041`**.
- **Every migration is additive and must not break a connected app.** Each
  carries a header stating what it adds, what it does not change, and **the
  rollback** — including "there is none, and here is why" when a `create table`
  is not reversible without data loss.
- **Follow the DEPLOYED tenant column name when extending a deployed table.**
  `supabase/migrations/0015_execution_evidence_module.sql:1-11` records the
  deviation deliberately: the workspace table is `public.organizations`, state
  columns are `text + check` rather than enums, and hashes are `text` with a hex
  check. `technical/database/schema-v0.1.sql` is the **shape** to build toward,
  not a file to transcribe. New tables use `workspace_id` and reference
  `public.organizations(id)`, which is what `0015` already does.
- **Tenant scoping is structural.** Every cross-aggregate reference carries the
  tenant column in a composite foreign key, so a cross-tenant row is
  unrepresentable rather than policy-denied. RLS is defence in depth, on every
  new table, keyed off `app.current_actor()`. No `FORCE ROW LEVEL SECURITY` on a
  table written by a `SECURITY DEFINER` owned by the same role.
- **Append-only tables get a `BEFORE UPDATE OR DELETE` trigger calling
  `app.reject_mutation()`.** Follow `0006` and `0016` for the shape.
- **Assert the required behaviour, never the current one.** A test that pins what
  the code does today defends the defect. Every test in this plan states the
  invariant identifier or the ADR clause it enforces, and fails before the code
  that satisfies it exists.
- **Refusals are proved by test from M3 onward** (version-0.1.md
  §"Cross-milestone rules"). A screen that displays «не готово» closes nothing.
- **Synthetic fixture names use the «Приклад-» prefix.** Never a plausible
  invented Ukrainian company name.
- **Every regulatory string is governed by
  [hidden-works-content-rules.md](../../product/hidden-works-content-rules.md),
  without exception.** A string with no `verification` tag and no source must be
  **unstorable**, not merely unrendered — the constraint lives in the column
  definition. Nothing in this plan adds a Додаток Н item, a Додаток В field, or a
  clause number.
- **Adding a capability to v0.1 requires an ADR, not a task.** "It is already in
  the DDL", "the catalog has the row", and "it is one more table" are explicitly
  not reasons (ADR-006 replacement rule 1). The test is: name the numbered step
  it is necessary for.
- **Do not delete the frozen importer** (ADR-006 decision 6). Its six operations
  and four tables stay, keep working, and get no extension work.
- **`apps/mobile` is not deleted and not built** (ADR-007 decision 2).

## Dependency order across M0–M6, and what breaks if it is reversed

The order is **M1 → M2 → M3 → M4 → M5 → M6, with M0 in parallel and gating M6**.
Each arrow below is a structural dependency, not a preference.

### M0 is parallel, and it is numbered 0 rather than 5.5

M0 builds no table and no operation, so it blocks nothing technically. It is
numbered 0 because a list with no milestone gets done last, and on a one-person
project last means never (ADR-006 decision 7). **Reversing it — running M0 after
M6 — is a boundary violation**: M6 is the pilot, the pilot puts a real
subcontractor's personal data and a real client's commercial data in the
environment, and M0 is the set of gates that make the environment fit to hold
them. ADR-006 replacement rule 5 forbids the reordering outright.

One M0 gate has a hard ordering consequence inside M1: **gate 10 (regulatory
content) requires the ДБН retrieval record** — exact URL, retrieval date, SHA-256
— committed under `technical/requirements/`
([hidden-works-content-rules.md](../../product/hidden-works-content-rules.md)
§"Open items"). Until it exists, the twelve `VERIFIED_PRIMARY` rows M1 seeds rest
on one download no reviewer can reopen. M1 can build the table and the constraint
without it; **M4 cannot render a `VERIFIED_PRIMARY` string in a customer-facing
artifact until it lands**, because the rule is that a source nobody can reopen
leaves the tag asserted and the source gone.

### M1 → M2: an occurrence has nothing to be materialised from

`requirement_occurrences` pins `rule_version_id`
(`technical/database/schema-v0.1.sql:1120-1121`; relationship-catalog.csv:53) and
copies the nine rule fields into itself. The only v0.1 source of a rule version is
`requirement_rule_versions`, and the only thing that says *which* versions apply
to a baseline is `contract_version_rule_bindings`. Both are M1.

**Reversed**, M2 would have to invent the obligation set at assignment time from
something — which is exactly `requirement_occurrences.create`, the hand-made
obligation that ADR-006 removes from v0.1 ("a hand-made obligation is also a
hand-removed one"). The gate would then rest on someone remembering to create the
right rows, which is the same as having no gate.

### M1 → M1 internally: the binding must precede the publication refusal

`contract_versions.bind_rules` targets a **draft** version
(`POST /v1/contract-versions/{versionId}/rule-bindings`) and
`contract_versions.publish` **refuses** a version with no bound set (INV-083).
Build the binding first; the refusal has nothing to check otherwise. This ordering
is what closes the standing contradiction ADR-006 decision 3 names — rules bind at
publication, published versions are immutable, and while binding was an M2
operation every M1 baseline was permanently outside the gate.

### M2 → M3: the refusal has nothing to refuse

`can_close_stage(s)` quantifies over occurrences applicable to `s`
(ADR-005 decision 7). With no occurrences, the predicate is vacuously true for
every stage and the closure command refuses nothing.

**Reversed**, M3 ships a command that always succeeds and a test suite that
asserts a refusal it can only produce by fabricating an occurrence. The milestone
whose entire outcome is a refusal would close on a fixture.

### M3 → M4: the act is assembled only from recorded facts

An act version is pinned by the **stage closure** in v0.1 (ADR-006 decision 4.5;
INV-084), and assembled only from progress entries already recorded, evidence
already `available`, and occurrence decisions already made. Without `stage_closures`
there is no pin, and without `requirement_evidence_decisions` the act would print a
decision block for a decision that does not exist.

**Reversed**, M4 produces a document that asserts closure without a closure — the
exact artifact ADR-005 decision 10 exists to make impossible.

### M3 → M5, and the M3/M5 approver-role interlock

M5's external decision is written against a **requirement occurrence** and its
receipt is carried by `external_decision_batches`, which
`requirement_evidence_decisions` requires on every externally submitted decision
(`technical/database/schema-v0.1.sql:1278-1283`). The decision table is M3.

The interlock runs the other way too, and it is a real constraint on M3's code:
**while M5 is open, the rule publication command must enforce that a `hold` names
an internal approver role** (INV-085; version-0.1.md §M3 exit gates). A `hold`
whose approver is external, published before the external link exists, is a stage
nobody can close — the approver cannot be reached. M5 lifts that restriction *by
the same change that ships the occurrence grant*. Shipping M5 without lifting it
leaves the external arc unreachable; lifting it before M5 ships produces
permanently blocked stages in the pilot's own baseline.

### M5 → M6, and M0 → M6

M6 is one query. Its numerator — the blocked-money sum — reads `blocked_reasons`
(M3) and prices from `work_items` (M1). It does not technically need M5. It is
ordered last anyway for two reasons, both binding:

1. **M6 is the pilot** (ADR-006 decision 8). The pilot loop it measures runs
   through the link, so M5 must exist for the loop to complete;
2. **M6 does not open until M0 is closed**, and until every field of the pilot
   record is filled — named partner, named **adversarial** технагляд, success
   measures, pre-gate baseline, sample, stopping conditions. **All six were empty
   as of 2026-08-06.** Filling them is discovery work, not delivery work, and no
   task in this plan does it.

### The one ordering this plan changes, and why it needs approval first

See §"Contradiction 5" below: `requirement_occurrences` is M2 and `work_stages` is
M3, but a `before_concealment` occurrence structurally requires a concealed stage.
The proposed resolution moves the **table** `work_stages` into M2's migration set
while leaving the **operation** `work_stages.create` in M3. That is a build-order
change inside v0.1 and adds no table to the 26 and no operation to the 58 — but it
changes what version-0.1.md §M2 §"Schema slice" says M2 builds, so it is raised as
a decision and not taken silently.

## Where existing code contradicts the new spec

Eight, each with file and line, what must change, and whether the change is
additive or a behaviour change. Every one was found by reading the tree; **none
was confirmed by running anything.**

### 1. `work_assignments.requirement_template_version_id` pins one optional template

**Where.**

- `supabase/migrations/0015_execution_evidence_module.sql:85` —
  `requirement_template_version_id uuid,` on `public.work_assignments`, nullable.
- `supabase/migrations/0015_execution_evidence_module.sql:104-107` — the composite
  FK into `requirement_template_versions`, with a comment saying it is
  *stricter* than `schema-v0.1.sql`.
- `supabase/migrations/0023_evidence_binding_hardening.sql:40-48` — the generated
  `pinned_template_status` column and the second composite FK that makes pinning a
  **draft** template unrepresentable.

**What the spec says.** ADR-005 decision 2, verbatim: this «**replaces** the
current model — one optional nullable template pinned per assignment
(`supabase/migrations/0015_execution_evidence_module.sql:85`).
`work_assignments.requirement_template_version_id` is retired; a template pinned to
an assignment cannot express a set, cannot vary by stage or location, and is
absent by default, which is the same as having no gate.» Rules bind at
contract-version publication instead; occurrences are materialised at assignment
creation from the bound rule versions.

**What must change.** In M2, a migration retires the pin: the column stops being
written by any command, the `assignments.create` route stops accepting it, and the
column is left in place with a comment recording that it is deployed lineage and
never written again. `entity-catalog.csv:22` already states this outcome
(«`requirement_template_version_id` is retired (ADR-005 decision 2)»).

**Additive or behaviour change.** **Behaviour change**, and a two-sided one.
Dropping the column would be a destructive migration against applied history, so
the column stays; what changes is that nothing writes it. Note the consequence
carefully: the two FKs above are what today guarantee a pinned template exists and
is published. Once nothing writes the column, those FKs guarantee nothing, because
the value is always NULL. **The guarantee they provided must be re-established on
the new path** — `contract_version_rule_bindings` must make an unpublished or
foreign-workspace rule version unbindable, by exactly the same composite-FK
technique (`schema-v0.1.sql:1035-1042` shows the shape). Retiring the old pin
without building the new guarantee is a net loss of enforcement, not a refactor.

### 2. `requirement_template_versions` is retired, not deferred

**Where.**

- `supabase/migrations/0015_execution_evidence_module.sql:36-66` — the table.
- `supabase/migrations/0015_execution_evidence_module.sql:46` —
  `severity text not null default 'blocking' check (severity in ('blocking','advisory'))`,
  the free severity axis.
- `apps/app/app/v1/workspaces/[workspaceId]/requirement-templates/route.ts` and
  `apps/app/app/v1/requirement-templates/[templateVersionId]/publish/route.ts` —
  the two live authoring routes.
- `packages/domain/src/authz.ts:4,16,17` — the `requirement_templates.manage`
  capability, held by `owner` and `admin`.
- `technical/permissions/responsibility-presets.csv:6` — the `requirement_owner`
  preset, corrected on 2026-08-06 to stop mapping to that capability.

**What the spec says.** [glossary.md](../../domain/glossary.md):232 retires the
term. `entity-catalog.csv:30` is explicit: «DEPLOYED (migration 0015) AND RETIRED
RATHER THAN DEFERRED … It is **NOT** a v0.1 build target and not v0.2 build work.»
ADR-005 decision 4 retires `severity` as a free axis — a requirement's consequence
is `blocking_scope`, and one column says so.

**What must change.** Three things, and the difference between them matters:

- the **table** is not dropped (applied migrations are append-only) and is not
  extended. It keeps its `v0.1-M2` marker because that is where it exists in the
  runtime, not because v0.1 builds it;
- the **authoring path** — two routes, one capability, one `@goproceed/contracts`
  module, one responsibility preset — is a **removal slice of its own**, recorded
  as owed in version-0.1.md §M1 and not yet scheduled. Until it lands, v0.1 ships
  a way to author a retired model. This plan schedules it as **M2 Task R** rather
  than leaving it floating, because M2 is the milestone that retires the pin the
  authoring path feeds;
- `severity` is retired as an axis. Nothing new reads it; `requirement_rule_versions`
  carries `blocking_scope` and no `severity` column.

**Additive or behaviour change.** The table comment is additive. The route and
capability removal is a **behaviour change and an API removal** — a caller holding
`requirement_templates.manage` loses two operations. Both operations are v0.1-M1
rows of `scope-v0.1.csv`, so removing them is also a route-set edit and cannot be
done by deleting files alone.

### 3. The upload-intent route reads the pinned template for its MIME allowlist

**Where.** `apps/app/app/v1/assignments/[assignmentId]/upload-intents/route.ts`:

- `:16-20` — `FALLBACK_MEDIA`, «Applies when the assignment pins no requirement
  template»;
- `:40` — selects `requirement_template_version_id` off the assignment;
- `:54-65` — «The pinned template is the authority on what may be uploaded; the
  fallback exists only for assignments that pin nothing», then reads
  `allowed_media` from `requirement_template_versions`;
- `:69-80` — the two 422 refusals built from `media.mimeTypes` and
  `media.maxByteSize`.

**Why this is the sharpest of the three.** Retiring the pin (contradiction 1) makes
`templateVersionId` permanently NULL, so `:57` is never entered and **every upload
silently falls back to `FALLBACK_MEDIA`** — 50 MB and four MIME types, for every
requirement in the product. The template CHECK added by
`supabase/migrations/0023_evidence_binding_hardening.sql:57-63`, which exists
precisely so a malformed `allowed_media` cannot widen the gate, stops being
reachable at the same moment. Nothing fails; the gate just gets wider, which is
the failure mode the whole ADR is written against.

**What must change.** The media policy must come from the **requirement occurrence**
the intent is captured against. `requirement_rule_versions` carries `allowed_media`
in the target design (`technical/database/schema-v0.1.sql:967`), the occurrence
copies it, and `upload_intents.requirement_occurrence_id`
(`supabase/migrations/0015_execution_evidence_module.sql:251`) is the binding that
names it. So: `upload_intents.create` gains the occurrence in its request, resolves
`allowed_media` from the occurrence, and `FALLBACK_MEDIA` becomes the policy for an
intent with **no** occurrence — with the same two refusals and the same error
messages, which are required by the failure table in
[execution-and-evidence.md](../../domain/execution-and-evidence.md) to name the
exact limit.

**Additive or behaviour change.** **Behaviour change**, and it must land in the
same migration/route change as contradiction 1, not after it. If the pin is retired
first and the occurrence source added second, the window between them is a period
in which the media gate is the fallback for everything. Sequence it as: add the
occurrence source, then retire the pin, then remove the template read.

### 4. `progress.record` carves valuation with no evidence precondition

**Where.** `apps/app/app/v1/assignments/[assignmentId]/progress/route.ts:85-90` —
`app.open_allocation_head(...)` followed immediately by
`appendValuationAllocation(...)`, which returns `net`/`tax`/`gross` minor units in
the 201 response (`:103-116`). The only preconditions checked are membership, the
`progress.record` capability (`:38-40`), assignment status `active` (`:42-46`) and
unit precision (`:53-72`).

**What the spec says, and what it does not.** Two rules apply and they pull in
opposite directions, so both are stated:

- **INV-065 stands and is not weakened.** «`progress.record`, `progress.adjust` and
  `upload_intents.*` carry **no** readiness predicate — the gate never refuses to
  record a fact» (version-0.1.md §M2 exit gates). The route must keep recording the
  quantity under a live block. **No task in this plan adds a readiness check to the
  recording path**, and a reviewer who asks for one should be shown this paragraph;
- **the valuation carve is a different act from the record.** ADR-006 decision 5
  moves the whole allocation ledger — `progress_allocation_heads`,
  `valuation_allocations`, `progress_claim_allocations` — to v0.2, because «it
  carves minor units out of a work-item pool for admission into a claim. Nothing in
  v0.1 is admitted to anything.» version-0.1.md §M2 §"Schema slice" repeats it: «the
  deployed allocation-ledger tables keep working and are not extended».

**The contradiction.** The route performs a **v0.2 act** — carving priced minor
units into a ledger — as a side effect of a v0.1 command, and returns the money in
the response body. In v0.1 there is nothing to admit that money to, and ADR-001's
financial boundary (untouched by ADR-006, and «easier to keep, not harder» in a
version that creates no accounting entry) is what the carve sits next to.

**What must change, and what must not.** The recording of the fact must not change.
What must be decided is whether the carve stays as a deployed no-consequence
side effect or stops being performed. This plan does **not** decide it, for a
stated reason: `valuation_allocations` and `progress_allocation_heads` are
**deployed**, ADR-006 decision 4 says «what moves to v0.2 is the **work**, never the
row», and stopping a write that a deployed table's own invariants (INV-025, tested
in `packages/testing/src/m2-*.test.ts`) may depend on is not a decision a plan
should take from static reading. **The task is to raise it, with this analysis, at
the M2 design gate**, and to add one test either way: that `progress.record`
succeeds while a `hold` on the assignment's occurrence is unmet (INV-065, required
behaviour, must be written regardless).

The narrower defect inside it *is* actionable and is scheduled: the 201 body
returns `netMinorUnits`/`taxMinorUnits`/`grossMinorUnits` to a v0.1 caller. **Blocked
value is exposure, never a receivable** (version-0.1.md §M6), and a per-measurement
money figure on the recording path is the easiest thing in the product to mistake
for one. M2 adds a test that no v0.1 surface renders it as an amount owed.

### 5. A `before_concealment` occurrence needs a stage, and stages are a milestone later

**Where.**

- `technical/database/schema-v0.1.sql:1133` —
  `check (timing <> 'before_concealment' or stage_is_concealed is true)`;
- `technical/database/schema-v0.1.sql:1118-1119` — the occurrence's composite FK
  into `work_stages (workspace_id, project_id, id, is_concealed)`;
- `technical/database/schema-v0.1.sql:652-686` — `work_stages`, whose
  `unique (workspace_id, project_id, id, is_concealed)` is what that FK pins.

**The contradiction.** `requirement_occurrences` is **M2**
(`entity-catalog.csv:35`; ADR-006 decision 4) and `work_stages` is **M3**. ADR-006
step 2 is «what must be photographed **before covering**» — that is
`timing = 'before_concealment'`, which is the entire hidden-works case and
therefore essentially every v0.1 occurrence. Under the CHECK above, such an
occurrence **cannot be stored without a concealed stage row**. So M2's central
exit gate — occurrences materialised at assignment creation, visible before work
starts — is unreachable with M3's table absent.

`relationship-catalog.csv:52` marks the occurrence→stage relationship
`required = no`, which is true of the column and does not dissolve this: the CHECK
is conditional on `timing`, and the timing v0.1 needs is the one that makes the
stage mandatory.

**What must change — a decision, not a task.** Two options, and this plan
recommends the first:

- **(A) Build `work_stages` in M2's migration set; ship `work_stages.create` in
  M3.** The stage set is derivable without a member command: the `stage_key`
  values bound to a contract version **are** that version's stage vocabulary
  (`technical/database/schema-v0.1.sql:1044-1045`), so `assignments.create`
  materialises the stages and the occurrences in one transaction, from the same
  binding. Adds no table to the 26 and no operation to the 58; M3 then adds the
  member-plane command for stages the baseline did not imply. Cost: version-0.1.md
  §M2 §"Schema slice" says M2 builds one table, and this makes it two.
- **(B) Keep the split and materialise `before_concealment` occurrences without a
  stage.** Requires relaxing the CHECK, which is the one structural guarantee that
  «a requirement that must precede a covering that never happens is unreachable»
  (`schema-v0.1.sql:1131-1133`, citing execution-and-evidence.md §"Timing"). Not
  recommended: it trades a build-order inconvenience for a permanently weaker
  schema.

**Additive or behaviour change.** (A) is **additive** to the schema and a
**scope-document correction** — version-0.1.md's M2 schema slice and its
"builds one" sentence need one edit each. Raise it at the M2 design gate before
writing the migration.

### 6. The `hold` CHECK in the target DDL contradicts ADR-006 decision 4.4

**Where.**

- `technical/database/schema-v0.1.sql:997` —
  `check (intervention_type <> 'hold' or blocking_scope = 'blocks_both')` on
  `requirement_rule_versions`;
- `technical/database/schema-v0.1.sql:1128` — the same CHECK, copied onto
  `requirement_occurrences`, commented «INV-066: the copied scope obeys the same
  rule as the published version».

**What the spec says.** ADR-006 decision 4.4: «**A v0.1 `hold` is
`blocks_stage_closure`, not `blocks_both`.**» version-0.1.md §M1 exit gates is
explicit about the mechanism: the **publication command** rejects a `hold` whose
scope is anything other than `blocks_stage_closure`, and «the CHECK keeps all three
intervention types and all four blocking scopes, so v0.2 is additive and no v0.1
record is reinterpreted». `capabilities.csv` (`requirement_rules.manage`) says the
same, and names both refusals INV-082.

**What must change.** **Do not transcribe lines 997 and 1128.** Transcribed, they
make every v0.1 `hold` unstorable — the version cannot write the only scope it is
allowed to write. The v0.1 migration keeps the permissive CHECK (all three types,
all four scopes) and the **command** performs both refusals, with a test per
refusal (INV-082). The v0.2 widening migration then has rows to widen; with the
DDL CHECK in place there would be none, because none could ever have been written.

**Additive or behaviour change.** Neither — it is a **transcription error to avoid**
in code that does not exist yet. Recorded here because `schema-v0.1.sql` is
labelled the target DDL and the obvious way to build M1 is to copy it.

### 7. `requirement_rule_versions` references a table v0.1 does not build

**Where.** `technical/database/schema-v0.1.sql:989` —
`foreign key (workspace_id, requirement_rule_id) references public.requirement_rules (workspace_id, id)`,
and `relationship-catalog.csv:57` declares the same relationship.
`technical/database/schema-v0.1.sql:926` creates `public.requirement_rules`.

**What the spec says.** ADR-006 decision 4.1: «**`requirement_rules` is not in
v0.1.**» `entity-catalog.csv:31` marks it `v0.2`. It is not among the 26.

**What must change.** The M1 migration creates `requirement_rule_versions`
**without** that FK. `requirement_rule_id` stays as a `not null` lineage key with no
referent in v0.1, and the meaning it needs in v0.1 is carried by the version table's
own `unique (workspace_id, requirement_rule_id, version_no)` plus
`contract_version_rule_bindings`'s `unique (workspace_id, contract_version_id,
requirement_rule_id)` — which is the invariant that matters here: **one rule
contributes at most one version to a baseline**, so "what was agreed" is
unambiguous (`schema-v0.1.sql:1029-1031`). v0.2 adds `requirement_rules` and the
FK; that addition is additive because the key is already there and already unique.

**Additive or behaviour change.** A **deliberate omission** in new code, recorded
so a later reviewer reading `relationship-catalog.csv:57` does not read the missing
FK as an oversight. The migration header must say so.

### 8. No `origin_method` value exists for a PWA capture, so M2 cannot record one at all

**Where.**

- `packages/contracts/src/uploads.ts:9` —
  `originMethod: z.enum(["native_camera", "photo_picker", "file_picker", "form"])`
  — four values;
- `supabase/migrations/0015_execution_evidence_module.sql:254-255` and `:311-312` —
  `check (origin_method in ('native_camera','photo_picker','file_picker','form','import','generated_derivative'))`
  — six values, on `upload_intents` and on `evidence_objects`;
- `technical/database/schema-v0.1.sql:97` — the target enum, which **does** carry
  `origin_not_distinguished` as a seventh value;
- `technical/states/state-catalog.csv:127` — the token, added 2026-08-06, marked
  «IT DOES NOT YET EXIST WHERE IT MUST».

**What the spec says.** ADR-007 decision 5: no object captured through the PWA may
be recorded with a value that asserts a native camera session; the domain layer must
carry a value meaning the origin is **not distinguished**. INV-086 states the
consequence plainly: **until the token lands, no PWA capture may be recorded at
all.**

**What must change.** An M2 migration widens both CHECKs to admit
`origin_not_distinguished`, and `packages/contracts/src/uploads.ts` gains the value.
The PWA sends it and never `native_camera`. A test asserts that a request carrying
`native_camera` from the PWA client build is rejected — the required behaviour, not
the current one.

**Additive or behaviour change.** The CHECK widening and the contract enum are
**additive**. The refusal of `native_camera` on the PWA path is a **new behaviour**
with no current counterpart, because there is no PWA.

milestone does not close because an identifier is listed, it closes because the
evidence line is recorded.

### M0 — Fit to hold someone else's data

  string with no `verification` tag and no source is unstorable); tenant isolation

  grant: from this milestone the rule publication command may accept an **external**
  approver role on a `hold`.
- **`LINK_CONFIRMATION` is level 3** of the assurance ladder and is stated, in the UI
  and **on every printed page**, not to be an electronic signature.
- **Acceptance evidence:** an **adversarial** технагляд opens the link with no account,
  reads the requirement in the standard's own wording with the photo, and **returns it
  with a reason**; the return is visible as a refusal on the closure; the crew corrects
  and the decision is retaken. A технагляд who refuses to open the link, refuses to
  decide inside it, or demands paper **invalidates A-3 and is recorded as a result,
  not as a bug**.
- **The v0.1 link decides a requirement occurrence, not the act.** An external `hold`
  must be decidable before closure, so the decision precedes the act and the act then
  carries it as a recorded fact. Whether the технагляд also wants to accept the act
  inside the link is a **pilot finding to record**, and it is not built.

### M6 — The blocked money

- **Tables built:** none. It is a query over `blocked_reasons` and `work_items`.
- **Operations added (1):** `blocked_value.get`.
- **Invariants that must become enforceable:** INV-070 (per-assignment
  deduplication), INV-012 (currency separation), INV-038 (missing versus zero price
  stay distinct), INV-039 (over-contract performance excluded), INV-011/INV-037
  (rounding reconciliation including largest-remainder ties). **INV-071 has no v0.1
  form** — the seven-state projection is v0.2.
- **The sum, precisely:** the amount of the work lines under a **blocked stage**, at
  the price on the **published baseline**, attributed **once per assignment**, broken
  down by `blocked_reason.code`, summed **within one baseline and never across
  baselines in different currencies**. Missing price, zero price and over-contract
  performance are reported **beside** the sum, never folded into it. Blocked value is
  **exposure, never a receivable**: v0.1 creates no accounting entry, no payment
  obligation and no cross-currency total.
- **Blocked value is reported beside first-time acceptance rate and days-to-signature
  and never as the hero number.**
- **Two blockers on opening M6, neither of which is delivery work:**
  1. **M0 must be closed** — recorded dated evidence per gate;
  2. **the pilot record must be complete** — named partner, named adversarial
     технагляд, success measures, pre-gate baseline, sample, stopping conditions.
     **All six fields were empty as of 2026-08-06.**
- **A third blocker, recorded and unresolved:** the two headline measures have **no
  v0.1 definition**. [glossary.md](../../domain/glossary.md) defines first-time
  acceptance rate over **claim segments** and their first submission, and
  days-to-signature from the submission of a **frozen package version** to the
  terminal **commercial decision**. Segments, package versions, submissions and
  `commercial_decision` are all v0.2. Neither measure can be computed in v0.1 as
  written, and neither pre-gate baseline can be taken. **The glossary owes both
  definitions; this plan does not invent them**, and M6 cannot open on a baseline
  that has none. Behind it sits the second gap: both baselines must come from a
  partner's historical records, and the project holds zero customer documents.
- **Neither headline measure is computed inside the product in v0.1.** No operation in
  `scope-v0.1.csv` computes or stores either. Both are recorded **beside** the
  product, in the pilot record, by the owner.
- **Acceptance evidence:** the pilot loop, end to end, on a named object with a named
  adversarial технагляд — a hand-typed baseline, an occurrence read on the phone
  before work started, a refused closure, an attributed exception, a satisfied closure
  and its act, an external return and its correction, and the blocked-money screen —
  measured against a pre-gate baseline taken **before the gate is switched on**. **A
  pilot that cannot fail cannot succeed.**
- **Closing evidence:** the pilot findings document, plus the M0 evidence verified as
  still holding throughout the pilot.

## Two migrations owed to v0.2

Recorded here because work written during a pilot is the work most likely to be
looked at later, and both are silent failures if forgotten:

1. every `hold` written during v0.1 with `blocking_scope = blocks_stage_closure` is
   widened to `blocks_both` when packages ship, **with a test that fails if one v0.1
   row is left behind**. Without it, every requirement recorded during the pilot sits
   permanently outside the payment-eligibility half of the gate, and nobody would
   notice;
2. every act version written during v0.1, pinned by its stage closure, gains its
   package-version pin when packages ship, **with a test that fails if one is left
   behind**.

## M1 task decomposition, in the order this workflow will build it

Fourteen tasks. Migration numbers are assigned in order from `0041`; if another
branch consumes a number first, renumber forward and never reuse. Every task
follows: failing test, then implementation, then the test again, then commit.

**Before Task 1 — one decision must be taken by the owner or the design gate, and
it is inside M1:** where the twelve library rows live. `requirement_library_items`
is workspace-scoped in the catalogs (`workspace_id not null references workspaces`)
and workspace-independent reference content in
[domain-model.md](../../domain/domain-model.md). The schema comment settles the
shape in favour of the catalogs and the substance in favour of the document
(`technical/database/schema-v0.1.sql:920`). The consequence is that the rows cannot
be seeded by a migration — there is no workspace at migration time. **Proposed:**
the twelve rows are materialised **per workspace at `workspaces.create`**, from a
constant compiled from `technical/requirements/dbn-a31-5-2016-dodatok-n.csv`, with a
fidelity test that fails when the constant and the CSV diverge. Recorded
alternative: seed on first read. Do not start Task 2 until this is decided.

- [ ] **Task 1 — The schema guard, failing.**
  Create `packages/testing/src/m1r-schema.test.ts` asserting the three new tables
  exist with their columns, their composite uniques, their append-only triggers and
  RLS enabled. Model it on `packages/testing/src/m1-schema.test.ts` and
  `m2-schema.test.ts`. It must fail on the current tree with "relation does not
  exist". *(Cannot be executed here; the failure mode is stated so the owner can
  confirm it.)*

- [ ] **Task 2 — Migration `0041`: `requirement_library_items`.**
  Table, append-only trigger, RLS, grants. `verification` and `source_citation`
  `NOT NULL`; `normative_character` admits only `dovidkovyi`; `act_form_basis` only
  `product_assumption`; the Н.14≤5 / Н.15≤7 CHECK. Header states: additive; the
  rollback is `drop table` **only while empty**, and once a workspace has been
  provisioned it is not reversible without data loss.

  `packages/testing/src/requirement-library-fidelity.test.ts` asserting the twelve

## What cannot be verified in this environment, and what the owner must run

### Established by reading, and worth re-checking against a running system

- **33 tables, 40 migrations, next number `0041`.** Derived from file contents. A
  `CREATE TABLE` inside a `DO $$ ... $$` block or a string literal would be missed
  by the same pattern that produced the `fail` false positive; the count should be
  re-derived from `information_schema.tables` once a database exists.
- **30 of 58 operations routed.** A route file that exports the verb but throws
  immediately, or that is unreachable because of a middleware matcher, counts as
  routed here and is not routed in fact.
- **The eight contradictions.** Each is a reading of code against a document. Numbers
  1, 2, 6, 7 and 8 are textual and should hold. **Numbers 3, 4 and 5 are behavioural
  claims** — that the media gate silently widens once the pin is retired, that
  `progress.record` writes ledger rows with no evidence precondition, and that a
  `before_concealment` occurrence cannot be stored without a concealed stage — and
  each should be confirmed by a test **before** the fix is written, so that the fix
  is proved to fix something.

### Decisions this plan raises and does not take

   `invariant-catalog.csv` owes the row; this plan does not invent one.
6. **The two headline measures have no v0.1 definition** (M6). The glossary owes
   them, and M6 cannot open until it has them.
