## Standing statement, before anything else

**Nothing described in this document has been executed.** M1 through M6 and every test suite
named below were written in a checkout with no `node_modules`, no PostgreSQL, no Docker and no
Supabase CLI. Across all of them:

- no migration has been applied — not `0041`–`0044`, not `0045`, not `0046`, not `0047`, not
  `0048`, not `0049`, not `0050`, not `0051`. **`0001`–`0040` are applied history; `0041`–`0051`
  were written on this branch and have never run anywhere.** That line is the whole of the
  difference between "written" and "deployed" in this document, and every claim below about a
  table, a column, a CHECK, a trigger, a policy or a grant that `0041`–`0051` introduce is a claim
  about a **file**;
- no test has been run — not once, not partially, not "collected";
- no route has been invoked, in any environment;
- `pnpm`, `vitest`, `tsc`, `psql` and `supabase` were never executed.

The only checks performed were: reading; `node --experimental-strip-types --check` on each changed
TypeScript file, **which parses and does not typecheck**; `node scripts/validate-canonical-docs.mjs`,
which needs no database; and, for M4's content-fidelity suite, one throwaway `node` script that
extracted the four mandated disclaimers from
[`hidden-works-content-rules.md`](../../product/hidden-works-content-rules.md) and compared them
byte-for-byte against literals transcribed by hand from the renderer. **That comparison agreed.**
It is a check on the extractor and on the transcription, not a test run: the suite that contains
those assertions has never been executed.

No milestone below is closed by appearing here. Nothing in this repository may be described as
green, verified, or confirmed working. **The suites are written; whether they pass is unknown.**

### Three consequences that are not caveats

1. **M4 produces no document** — see the next subsection.
2. **M5 throttles nothing.** There is no rate limit on `/external/exchange` or on
   `/external/occurrence-decisions`, and none anywhere else in this product either.
   `technical/rate-limits.csv` has no row for either path. A per-grant failure counter is
   *unimplementable* as the protocol stands: a wrong token matches no row to count against. **This
   is the largest security gap v0.1 leaves**, it is stated in migration `0049` §11 and in
   `m5-external.int.test.ts`, and no test pretends otherwise. *(Qualified 2026-08-08: it is the
   largest **security** gap and it is not the most serious open defect. That is §5 item 63 — a
   foreman can move a work item's entire pool with one `progress.adjust`, which is an
   authorisation-bypass on money rather than on a door. Ranked together: item 63 first, then the
   external shell's auto-exchange (§5 item 64, which loses a grant silently and needs one line),
   then this, which needs a decision before it needs code.)*
3. **M6 is built and cannot close.** `blocked_value.get` exists, routes, sums and drills down. The
   two headline measures it is required to be reported *beside* — first-time acceptance rate and
   days-to-signature — **have no v0.1 definition**, and no slice may invent one. §5 carries this as
   the single M6-cannot-close blocker.

### One consequence that is not a caveat: M4 produces no document

`statutory_acts.render` **refuses in v0.1**, and `statutory_act_versions.freeze` refuses with it.
Not by a hardcoded `throw` — by two blockers derived from data this repository does not hold: the
enumerated **В.1/В.2 field list** of Додаток В (committed nowhere; `test-strategy.md:139-152` says
so and forbids substituting one typed from memory) and the **ДБН retrieval record** M0 gate 10 owes.
So M4 composes an act, returns every recorded fact it is assembled from, and **cannot lay it out,
cannot hash it, and cannot freeze it**. Two of the six steps of the plan's own M4 acceptance walk —
«render twice and diff the bytes» and «check the render field by field against the В.1/В.2 list» —
are therefore unperformable, and the suites assert the refusals rather than skipping the steps.
This is §5's blocking item 1a and it is the single largest gap M4 leaves behind.

**Stated as the mechanism, because «refuses in v0.1» reads as conditional and it is not**
*(added 2026-08-08, from the whole-build audit; the fact was known and the shape of it was written
down nowhere).* `DODATOK_V_TEMPLATE.fieldList` is `null` at
`apps/app/src/lib/statutory-act-form.ts:205`. `renderStatutoryAct` pushes
`dodatok_v_field_list_not_committed` for any template whose `fieldList` is null (`:510-521`) and
returns `{ ok: false }` whenever the blocker list is non-empty (`:526-528`). Neither test looks at
the act. So the render refuses **for every act, on every input, in every workspace** — there is no
composition a user could assemble, and no fixture a suite could build, that reaches a rendered
document. `statutory_act_versions.freeze` hashes the render and therefore **always refuses too**
(`.../freeze/route.ts:47-65`, which says so in its own header). `DBN_RETRIEVAL_RECORD` is `null` at
`:129` and is a second, independent, equally unconditional blocker: fixing one leaves the other.

**This is correct behaviour, and recording it as a blocker is not recording a defect.** Allow-list
item 3 licenses the product to print every field of В.1 and В.2 in the standard's order; it does not
supply them, and nothing in this repository does. Typing them from memory or from a secondary source
is the one act
[`hidden-works-content-rules.md`](../../product/hidden-works-content-rules.md) forbids without
qualification, and `test-strategy.md:139-152` extends the ban to fixtures because «a fixture looks
verified». A renderer is worse than a fixture: a caption invented here is printed onto a document a
client's lawyer reads and looks decided. **Refusing is the only correct behaviour available**, and
the value of the refusal is that it is derived from the absence rather than declared — it disappears
by itself on the day the data land.

**What unblocks it, exactly.** One artifact, and it is not code: the enumerated В.1/В.2 field list —
every field of both sections, in the standard's order, with **the standard's own captions** —
committed under `technical/requirements/` alongside `dbn-a31-5-2016-dodatok-n.csv`, in the same shape
as that file, carrying **per row** a `verification` tag and the **source** it was read from. It must
be transcribed from the primary ДБН А.3.1-5:2016 file by someone holding it, which is the same
retrieval that closes item 1b — so the two artifacts are one errand, not two. Then
`DODATOK_V_TEMPLATE.fieldList` is populated from that file and both blockers stop being produced.
**No route, schema, contract or test change is required**, and none should be attempted as a
substitute.

**Until it lands, M4 ships a composer and no document.** Three of the four M4 operations do their
whole job — `statutory_acts.compose` assembles an act version from recorded facts and refuses a
quantity nobody recorded, `statutory_acts.get` returns it, and the freeze **guard** is real and
tested from the table owner. The fourth produces nothing a person can be handed, and the milestone's
own user outcome in [`version-0.1.md`](../../delivery/version-0.1.md) §v0.1-M4 — «as a document
someone can print and hand over» — **is not met in v0.1 and cannot be met by any code in this
repository.** No statement anywhere in this package should describe M4 as closed on the strength of
the four routes existing.

## 4. Every judgement call, slice by slice

### 4.1 The ninth contradiction — the rule predicate has no left-hand side

**The fact.** A requirement rule is a predicate over (work type, stage). `public.work_items` has no
`work_type_key` — not in migration `0012:219-268`, not in `technical/database/schema-v0.1.sql`, not
in `createWorkItemRequest`. `glossary.md:109` calls the carrier "a key with no owning fact… giving
it one is a scope decision an ADR must make"; `entity-catalog.csv:40` records it as an unresolved
M1 entry condition. **Matching cannot run.** This is not in the plan's eight contradictions.

**The migration author stopped at that boundary.** The application slice could not, because it
ships the command. What it did:

`workTypeKeyOf(line)` returns `null` for every row, in one documented place, with both ways around
it named and rejected:

- **match everything** — every assignment gets every bound rule. A wrongly materialised `hold` can
  be cleared only by waiver or accepted risk (INV-063 forbids `not_applicable` on a hold), so it
  **forges permanent attributed entries** in the record the product exists to keep;
- **match nothing, quietly** — INV-072's failure exactly.

**Shipped: match nothing, never quietly.** `coverage: "work_type_unresolved"` travels in the 201
body, in a dedicated `requirement_occurrences.materialized` audit row, in the outbox payload, in the
list response, and in the dry run's per-line verdict plus a `diagnosis: "work_type_has_no_carrier"`.
`no_bindings` is a **separate** value, so M1 review finding 1 is not hidden behind the work-type
gap. A disclosed hole can be closed by the ADR that owns it; a forged waiver cannot be un-forged.

**CLOSED 2026-08-08 by migration 0050 — the carrier, not the owning entity.** `public.work_items`
gains a nullable `work_type_key`; `work_items.create`/`.update` write it and **refuse** a key that
names no rule version the workspace can bind (`app.work_type_key_is_bindable` +
`work_items_work_type_guard`), because a plain nullable column would have reintroduced silently the
very failure the null stub avoided loudly — one typo, no match, no occurrence, a vacuous closure,
and every per-row constraint still satisfied. `workTypeKeyOf` now reads the line, and matching runs.
Three things this did **not** do: it did not give the work type an **owning entity** (glossary.md:109
is unchanged — the vocabulary stays emergent, and migration 0050 §3 records what adding the entity
would cost in five documents and in the build-list validator); it did not touch the frozen importer,
so every imported line still carries NULL and is still reported `work_type_unresolved`; and it did
not make a null key an error. The dry run's summary value is renamed `work_type_has_no_carrier` →
**`no_work_line_is_typed`**, because the old name asserted a fact about the product that is no
longer true — the count is now zero because of the DATA, and the remedy is a superseding version
with typed lines rather than an ADR. `contract_versions.publish` reports by position every typed
line no **bound** rule version matches (ADR-006 decision 4.2 requires it be named, not refused) and
refuses only when **not one** typed line reaches the bound set.

**What that cost the test suite, stated plainly.** *(Updated 2026-08-08.)* This paragraph read
«Every assertion that goes through `assignments.create` about the CONTENT of the obligation set is
vacuous today, because both sides are empty», and that was true of every suite written before
migration `0050`. **It is no longer true of all of them.**
`apps/app/tests/materialisation-end-to-end.int.test.ts` types a line through `work_items.create`,
publishes, calls `assignments.create`, and compares the **stored** rule-version set against an
oracle computed in SQL from the stored work type and the stored bindings
(`IMPLIED_RULE_VERSIONS_SQL`, which never names a work type of its own) — both sides non-empty, and
the file says in terms that before `0050` its right-hand side could only have been written `toBe(0)`.
What remains vacuous is narrower and is a **fixture** property, not a product one: the four M3–M6
harnesses type no line, so for them both sides are still empty (§8). The two ways the suites dealt
with the original gap stand unchanged, and neither pins today's arithmetic:

- `planForWorkType` takes a supplied work type, so matching, stage derivation and ordering are
  exercised for real — in `requirement-materialisation.test.ts` against fixture rows, and in
  `m2-materialisation.int.test.ts` against a real published baseline whose implied set is computed
  by an **independent SQL query** over the bindings;
- the route-level assertions are written as the requirement ("the 201 reports exactly the rows it
  stored") and each one says on its own line that it is vacuous today.

`m2-materialisation.int.test.ts` contains a helper, `materialiseFor`, whose precondition throws an
explicit Error — not an `expect` — when the route has already materialised. **That message names
the single place the work-type slice must edit.**

### 4.4 Decisions taken while writing the tests

1. **Two integration fixtures, deliberately.** `requirement-occurrences.int.test.ts` builds one
   work type; `m2-materialisation.int.test.ts` builds **three bound rule versions across two work
   types**. With a single work type, "materialises exactly what the bindings imply" and
   "materialises everything the baseline bound" are the same sentence and no test can separate
   them. The second fixture exists to separate them.
2. **The exactness oracle is SQL, not the same filter run twice.** The expected set is computed by
   a query over `contract_version_rule_bindings`; the actual set comes from the planner. That
   compares the **matching**. It shares the join with `BOUND_RULE_VERSIONS_SQL` and therefore does
   not independently check the read — stated in the test.
3. **"The dry run writes nothing" is asserted over every base table in the schema**, not over the
   two tables the operation is about. The census asserts that exactly `audit_events` and
   `idempotency_records` change, and that a refused run changes nothing at all. "The dry run stores
   no occurrence" is the claim its name makes; "the dry run stores nothing else either" is the claim
   nobody would notice being broken.
4. **The database refusals are attempted from the table OWNER**, bypassing RLS, in
   `packages/testing`. The command that materialises is one caller and a future slice rewrites it;
   what must survive that rewrite is a foreign key, a CHECK or a trigger. A refusal only the planner
   performs is not asserted there at all.
5. **The fixture reaches a published-and-bound baseline the way the product does.** Binding is
   refused on a published version and an assignment is refused on a draft, so the fixture binds
   while the version is a draft and then performs the draft → published UPDATE, touching only the
   four columns `app.guard_contract_version()` permits. It does **not** disable the window guard: a
   fixture that suppressed it would build a state the product cannot produce, and every refusal
   tested against it would be tested against a fiction.
6. **Contradiction 6 is tested from both ends.** `hold` + `blocks_both` is *storable* (so the v0.2
   widening is an UPDATE and not a DDL change), the whole vocabulary is asserted present on both
   CHECKs, the **route** refuses to publish anything but `blocks_stage_closure`, and an occurrence
   claiming a scope its pinned version does not have is refused by the FK. That last one is what
   makes the v0.2 widening a single statement over two tables.
7. **The write policy is proved to be a capability check and not a role check.** The seeded owner
   holds `project.admin` and *not* `assignments.manage`; the insert is refused, then admitted once
   the capability is granted. Both halves are needed — a policy nobody can satisfy fails closed and
   is still broken.
8. **The upload gate's size limit is tested separately from its media list.** A gate that read the
   MIME types from the occurrence and kept the fallback's 50 MB ceiling would pass every
   media-type test ever written and still accept ten times what the requirement permits.
9. **The occurrence is proved to beat the retired template pin**, using a template that allows
   `image/png` and a rule version that allows only `image/jpeg`. If the order were reversed, the
   png would pass — so the test distinguishes the two orders rather than asserting that both
   sources exist.
10. **Vacuous assertions are labelled, and only where they state the requirement.** No test asserts
    "materialisation produces nothing"; that is today's arithmetic and pinning it would make the
    suite defend the gap.

### 4.5 One defect the test-writing found, and fixed

**Migration `0044` made every existing rule-version fixture unstorable, and nothing said so.**

`0044` added `requirement_rule_versions_allowed_media_check`: for `evidence_kind` in
(`photo`, `document`), `allowed_media` must be the `{mimeTypes, maxByteSize}` object. The column's
default is `'[]'::jsonb`, and **both** direct writers in the test suite relied on that default while
taking the default evidence kind, `photo`:

- `packages/testing/src/m1-rules-fixture.ts` `seedRuleVersion`, which every M1 rules suite and both
  new M2 suites call;
- the inline INSERT in `packages/testing/src/m1-rules-rls.test.ts:146`, including its own positive
  control.

Applied against a running database, every one of those rows would have been rejected with a 23514
**inside the fixture**, so the M1 and M2 database suites would have failed before reaching an
assertion. Both writers now write `allowed_media` explicitly, `RuleVersionSeed` gained an
`allowedMedia` override so the CHECK itself can be exercised, and four cases in
`m2-occurrences-schema.test.ts` exercise it — including `{}`, the shape a CHECK written without
`coalesce` would have admitted.

This was found by reading `0044` while writing tests against it. **It has not been run**, so it is
a defect found and repaired by reading, and the repair is unverified like everything else here.

2. **`closed_without_evidence` stays unreachable and `public.unevidenced_closures` is not built**

6. **The exception is permitted to the member who recorded the progress.** INV-069 is about

### 4.7 Decisions taken in M4's migration (`0047`)

Seven of them are departures from `technical/database/schema-v0.1.sql`, and each is named in the
migration with the reason.

1. **The printed quantity is a ROW, not four columns.** The target gives one
   `root_progress_entry_id`/share/quantity/unit; ADR-005 decision 10 says the composer offers
   `quantity_entries` — **plural**. With a single quadruple a composer facing three recorded entries
   can only drop two or print their sum, **and their sum is not any recorded entry**: it is a
   free-text quantity that arrived through arithmetic instead of a keyboard, which INV-073 does not
   distinguish.
2. **Three signatory slots are ROWS with typed columns, not three `jsonb` columns.** Three blobs stop
   a fourth *slot* and do nothing about a banned *field*: «ким видана» is a key inside a blob, added
   without a migration and reviewed by nobody. Here a fourth slot violates a primary key over a
   three-value CHECK, and a banned field needs a migration somebody reads.
3. **`statutory_acts` is append-only.** The target has `version`/`updated_at`; nothing on the identity
   row can move, and everything a composer edits lives on the draft version.
4. **The version lineage is contiguous, unforked and single-drafted** — the predecessor ordinal is
   CHECK-forced to `version_no - 1`, a self-FK pins the predecessor's status to `frozen`, and a
   partial unique index allows one draft per act.
5. **Form В only, through one named removable constraint.** `'dodatok_g'` stays in the vocabulary so
   v0.2 is additive, and `statutory_acts_v01_form_v_only_check` is the single constraint that slice
   drops.
6. **No frozen evidence set on the act.** `stage_closure_occurrences` already is one and cannot gain
   a member after the closure's transaction; a second copy could only disagree.
7. **Every table carries `project_id`** for RLS.

And the judgements the specification did not settle:

8. **The slot→relationship map is stated by no document.** п. 8.4.3.5's three roles onto
   `project_parties.relationship`'s seven values: технагляд→`technical_supervision`, авторський
   нагляд→`designer`, будівельна організація→one of
   `general_contractor`/`subcontractor`/`performer`. **The builder leg is the guess.** Enforced by one
   named constraint so a pilot that needs another mapping changes something findable.
9. **авторський нагляд is optional at freeze**, following `schema-v0.1.sql:1656-1657`. п. 8.4.3.5 names
   three and nothing says the third is conditional.
10. **Zero printed quantities is representable**, because the target's quadruple is entirely nullable.
    Whether Додаток В's field list makes a quantity mandatory is exactly what is not established.
11. **A share too small to print at the unit's precision is UNSTORABLE.** Deliberate — «an act that
    prints «0.000» as the quantity performed is worse than an act that refuses to be composed» — and
    it is a refusal nobody specified.
12. **The rounding mode is not fixed by the schema.** INV-011/INV-037 are about money; no document
    states a quantity rounding rule, so the CHECK bounds the printed value to within one unit in the
    last place and admits half-up, half-even and truncation alike.
13. **`registry_checked_on` is required at freeze**, with one day of slack on the future-date guard as
    a **timezone allowance and not a business rule**.
14. **`form_template_hash` was added beyond the target**, so a render divergence has a nameable cause.
15. **Reads sit behind `statutory_acts.compose`**, because `capabilities.csv:32` puts all four
    operations there — so a member who may read an act may compose one. `project.admin` is admitted
    alongside so the pilot owner is not locked out.
16. **The party FK carries `relationship`**, so an in-place UPDATE of a project party's role is
    refused while an act names it. Latent today (no v0.1 route writes that column) and deliberate.
17. **`frozen_organization_name_source` is a two-value vocabulary invented here**
    (`legal_profile_official_name` / `party_display_name`) to keep a frozen string from being free
    text.

### 4.8 Decisions taken in M4's application slice

1. **Freeze refuses when render refuses.** `content_hash` is the digest *of the render*. Hashing the
   frozen inputs instead would let freeze succeed today and would redefine a column `0047` defined in
   the same run. The coupling was chosen.
2. **Render refuses a DRAFT.** No document says either way. The cost is real: a composer cannot
   preview the laid-out form before an irreversible freeze. `statutory_acts.get` returns every
   assembled fact, so what is unavailable is the layout and not the content.
3. **An internal member evidence decision is ladder level 2, `operational acknowledgement`.** Level 2's
   own row says «No legal effect», and a технагляд's acceptance is arguably more — but «arguably more»
   is not a level, and the ladder grades mechanisms.
4. **An occurrence satisfied by an EXCEPTION is level 2 as well.** Same mechanism, no decision row, no
   `assurance_label`. Stated by nothing.
5. **The ladder's level names print in the ladder's own English.** It gives no Ukrainian translation
   anywhere in this repository, and inventing one for a legal-adjacent label on a regulated document
   is the failure class this work exists to avoid. The Ukrainian sentence that matters — the level-3
   denial — is mandated verbatim and printed.
6. **The quantity rounding midpoint is read off `contract_versions.rounding_policy`** — the baseline's
   own pinned rule, which is a recorded fact, rather than a constant in code. **Applying a money rule
   to a quantity is the product's assumption.**
7. **`frozen_organization_name_source`:** the legal profile's `official_name` is preferred over
   `parties.display_name`, and `source_party_version` is the version of the record the **name** came
   from. Freezing the display name and recording the legal profile's version would make the pair
   unreadable.
8. **`act_form_basis` is always written `'product_assumption'`.** `user_selected` has no v0.1 producer,
   because v0.1 stores form В only and there is nothing to select.
9. **`PACKAGE_BLOCKED` carries the render refusal.** **No code in `technical/error-catalog.csv`
   describes «a regulatory content artifact this document needs is not committed»**, and one was not
   invented. `PACKAGE_BLOCKED` is the only existing code whose shape matches — non-retryable 4xx,
   `resolve_listed_blockers`, log policy `counts_codes` — but its catalogued producer names packages,
   which v0.1 does not have at all. **The catalog is owed an act-shaped row.**
10. **`VERSION_CONFLICT` carries the stage-state refusal**, following `stage_closures.create`'s
    precedent. `PROJECT_STATE_CONFLICT` and `CONTRACT_STATE_CONFLICT` exist for their entities;
    **there is no work-stage state-conflict code.**
11. **The prohibition-G note's Ukrainian wording is unsourced product copy.** ADR-005 decision 10
    mandates the label, not its words, and `technical/copy-catalog.csv` carries **no row for the act
    render at all**. The sentence written *denies* that the norm establishes the mapping, so it
    asserts nothing regulatory — and no reviewer has approved it.
12. **The act prints the довідковий disclaimer.** Its decision blocks reproduce Додаток Н acceptance
    criteria with Додаток Н citations, which is a generated requirement list in substance. Printing it
    where it may not be strictly required costs a paragraph; omitting it where it was required is
    prohibitions B and C.
13. **`FormFieldBinding`** (`static | quantity_lines | decision_blocks | signatory{slot}`) is an
    invention: a vocabulary of *this data model's* join points, not of the form. It forces whoever
    commits the field list to state per field what fills it, and there is deliberately no `free_text`
    binding.
14. **«В.1»/«В.2» print as `normative` blocks** sourced to allow-list item 3, which names them in terms.
15. **An unfilled `designer_supervision` field prints its caption and nothing.** A form that silently
    dropped an unfilled field would print as though it had three fields only sometimes.
16. **A member lacking the capability gets 404, not 403**, because `sav_select` hides the row.
    Deliberate cross-workspace (INV-001/INV-002 — no oracle); a legibility **cost** in-workspace. A
    `project.admin` still gets the 403.
17. **`project.view` is required on all four routes** beside `statutory_acts.compose`. Every fact
    table the act reads is behind `project.view`/`project.admin` and none behind the act capability,
    so without it the answer is an *empty act* rather than a denial — `readiness.get`'s finding, one
    milestone later.
18. **`quantityEntries` may be empty**, following `0047`'s completeness trigger.
19. **`compose` enqueues no outbox row.** `event-catalog.csv` carries exactly one act event,
    `statutory_act_version.frozen`. A `…composed` topic would be an invented event; composition is in
    the audit trail only.
20. **Freeze idempotency is `public.idempotency_records` and nothing else.** The freeze writes no new
    row, so it has no idempotency columns of its own, and this is the explicit statement `0047` §11

21. **Byte-determinism depends on zod's output key order.** `contentHash` itself is computed over a

### 4.9 Decisions taken while writing M4's tests

1. **The content rules are READ, not transcribed.** `tests/helpers/content-rules.ts` parses
   `docs/product/hidden-works-content-rules.md` at test time. A disclaimer pasted into a test is a
   second copy of a mandatory string, and the renderer's constant could then drift from the rule while
   both tests stayed green — because both would be comparing the renderer with itself.
2. **The comparison is over UTF-8 BYTES, not `===`.** A Latin «c» in «сформовано», a NO-BREAK SPACE or
   a different apostrophe reads identically and is a different string on a regulated form. A
   first-difference reporter prints the codepoint, because otherwise the failure looks like a broken
   test.
3. **The disclaimer COUNT is asserted.** Every other assertion asks about a string that exists; this is
   the one that notices a *fifth* mandated disclaimer the renderer does not print.
4. **Prohibition E's ban list is read out of prohibition E.** A field the document bans tomorrow is a
   field the sweep checks tomorrow, not on the day somebody remembers to widen an array.
5. **Prohibition B is the only prohibition swept over the whole renderer source**, comments included:
   «орієнтовн» occurs zero times in the standard, so it has no legitimate use in the module that
   renders the standard's form. The others cannot be swept that way — the module's comments quote «ким
   видана» and «наказ … № 115» precisely in order to record that they must not be printed — so those
   are swept over the exported constants instead.
6. **The prohibition-G note is NOT reached by any sweep.** Its two Ukrainian sentences are built inline
   in `renderStatutoryAct` and exported by nothing. Reported, not tested.
7. **No fixture invents a caption of Додаток В** — not even a transparently «Приклад-» one, because a
   fake caption in a fixture is the thing somebody copies into the template.
8. **The two obligations of the M4 fixture are satisfied DIFFERENTLY** — one by an accepting decision,
   one by an `accept_risk` exception. A mapper that walked only the decision branch would produce an
   act with one block where the closure froze two.
9. **The fixture order is forced by INV-069:** decide, then record progress, then except, then close.
   One member is all a v0.1 pilot has.
10. **`project_parties` and `party_contacts` are inserted directly, and that is reported as a GAP.**
    `scope-v0.1.csv` carries no operation that writes either table, so the three typed signatory slots
    name records **no v0.1 command can create**. A pilot workspace reaches `statutory_acts.compose`
    with nothing to put in any slot.
11. **`attemptFreeze` performs the route's own UPDATE**, because the route refuses and INV-015 is a
    claim about a frozen row. The integration suite asserts the refusal with its two blocker codes, so
    the day it lifts, that suite fails and this harness is the thing to delete.
12. **The storage refusals are attempted from the table OWNER**, RLS bypassed, in `packages/testing`:
    what must survive a rewrite of the four routes is a key, a CHECK or a trigger.
13. **Every leg of the six-column quantity key is attacked one at a time.** A key that resolves on five
    of six columns is a key that stopped nothing.
14. **Column CENSUSES, not pattern matches alone.** Both content tables have their full column set
    enumerated, so a later migration that adds a field prohibition E bans fails the test even if its
    name matches no pattern.
15. **The 404-vs-403 cost of `sav_select` is asserted rather than discovered**, in both directions: the
    `project.view`-only member sees nothing, the `project.admin` sees the row and is refused by name.
16. **One assertion deliberately does not pin a status code.** A signatory whose project role does not
    match the slot is refused by a CHECK and the caller sees whatever `toProblemResponse` makes of a
    23514; the test asserts only that nothing was composed, because the owed work is a legible 422 and
    pinning today's code would defend its absence.

### 4.10 Decisions taken in M5 — the link

Migration `0049` and the six routes. Each is a judgement the specification did not settle, and each
is written into the file that makes it.

1. **`recipient_email` is a departure from the target DDL.** `schema-v0.1.sql`'s grant carries
   `recipient_contact_id` and no address. **No v0.1 operation writes `party_contacts`** (§5 item 35),
   so requiring a contact would make `occurrence_grants.issue` unreachable in every pilot workspace.
   `entity-catalog.csv:8` says this row is where that is decided; it is decided against the contact,
   and the contact column stays for the day a command creates one.
2. **`permissions` is a CLOSED two-key vocabulary**, keyed by the capability ids
   `external.view_scope` and `external.decide_evidence` and CHECK-enforced.
   `external.decide_commercial` is deliberately **unrepresentable** in v0.1.
3. **A deciding grant is REFUSED when the occurrence's `approver_is_external` is false.** In no
   document. An internal obligation handed to a link would be discharged by an outsider. One
   condition, one place; observing grants are unaffected and may name any role.
4. **`revoke_reissue` carries a required `reissue` boolean.** Both `revoked` and `superseded` exist
   in `grant_status` with no other producer, and a link sent to the wrong address must be killable
   **without** minting another for the same address.
5. **`decide_role` and `decides_evidence` are CHECK-derived, not `GENERATED ALWAYS`.** A foreign key
   onto a generated column is a shape that cannot be checked without a database, and a migration
   that fails to *apply* is worse than one that needs two more written values.
6. **The batch's occurrence foreign key is three columns, not the target's two.** Otherwise
   `project_id` — which `edb_select` resolves capability against — would be free text on a row only
   the external plane inserts.
7. **The link is returned ONCE, in the 201 body, with `deliveredBy: "caller"`.** No email provider
   exists in this product; the v0.0 invitation command sets the precedent.
   `delivery.protected_link_email` has no producer.
8. **The link is attached OUTSIDE `withIdempotency`.** Inside it the raw token would be persisted in
   `idempotency_records.response_body` and INV-044 would be broken by the most ordinary-looking line
   in the file. A replay therefore returns the same 201 **with no link**, which is the same situation
   as a crashed send and is stated in the response.
9. **`external_decision_batches` is the external plane's idempotency record.**
   `idempotency_records`' policies are scoped to `user:<actor>` (migration 0006) and the external
   plane has no actor, so INV-007 is carried by a unique key on `(grant, idempotency key)` instead.
10. **The session rotates on submit, LAST.** Rotation revokes the current session and every external
    policy resolves through `status = 'active'`, so any write moved below it fails with a policy
    error that says nothing about rotation. Stated in the route.
11. **`occurrenceSatisfied` on the external receipt reports the DECISION disjunct only.** The
    exception head is not in the granted scope, deliberately: an external reviewer must not learn
    from a receipt that somebody waived the obligation they just decided.
12. **The CSRF verifier is a departure.** `external_sessions`' own table comment mandates a
    synchronizer token and gives it no column; one was added.
13. **A missing `Origin` header is a refusal, and `Referer` is not consulted as a fallback.** This
    surface sends `no-referrer`, so a `Referer` fallback could only ever be satisfied by requests
    this product did not originate.
14. **No third database role.** The empty actor GUC plus deny-by-default RLS buys the same
    isolation. The residual risk — a future table gaining a subject-blind policy — is what the
    reachable-set sweep in `m5-external-schema.test.ts` exists for.
15. **The reviewer does not get the photo.** `external.occurrence_scope` returns each evidence
    object's identity, media type, size, SHA-256 and provenance. No operation in `scope-v0.1.csv`
    streams an original to an external session and a seventh was not invented. **The M5 acceptance
    walk fails here for a buildable reason**, and the suite asserts what IS returned rather than a
    substitute.
16. **The scope identifies the obligation, not the object.** No project name, address or contract
    number: those rows are unreachable from the external plane by design. Whether a технагляд
    supervising three sites can act on that is a **pilot finding**, not a missing field.
17. **Nothing expires anything.** Both `expired` states are reachable only by a sweep, and there is
    no scheduled principal in this repository. Every expiry the product performs is a read-time
    comparison inside `app.external_session_scope()`; the stored status stays `active` on a row that
    is expired in fact.

### 4.11 Decisions taken in M6 — the blocked money

1. **The primary-cause precedence is TRANSCRIBED, not invented.** One work assignment can carry two
   unmet obligations whose codes differ, and ADR-005 decision 6 says its money is attributed **once**
   — so «under which code» is a question the sum cannot avoid.
   [`value-at-risk.md`](../../domain/value-at-risk.md) §"Two views, one of which is additive" fixes
   the order in a fenced block, sits at precedence level 2 (above the ADRs), and says in terms that
   ADR-005 does not fix it. That order is copied into
   `packages/contracts/src/blocked-value.ts` with its provenance. The same document calls the
   additive/non-additive pair «v0.2 machinery»; the *problem* it solves is not v0.2's, and the two
   available answers were to transcribe an approved order or to invent one.
2. **Both views ship, and only one is summable.** `byCause` is additive — each assignment's money
   under exactly one code; `affectedByCause` is not — each assignment under every code blocking it.
   The wire carries `byCauseIsAdditive: true` and `affectedByCauseIsAdditive: false` as **literals**,
   so a renderer cannot sum the wrong one without reading a `false`.
3. **The reconciliation is a SCHEMA rule, not a test.** `blockedValueResponse`'s `superRefine`
   refuses a response whose additive partition does not equal its own totals per currency and per
   component, whose non-additive view is smaller than its additive one, or whose cause rows name an
   occurrence in no drill-down target. A test checks the fixtures somebody thought of; this checks
   the pilot's own data on the day it is read, and turns a projection error into a 500 rather than a
   wrong number in a meeting with the general contractor.
4. **The baseline is a REPORTED DIMENSION.** version-0.1.md §v0.1-M6 requires the sum to be «within
   one baseline and never across baselines in different currencies», and currency separation alone
   does not carry that sentence — two baselines of one project can share a currency. `byBaseline`
   reconciles to the totals under the same rule as `byCause`.
5. **The baseline is read off the WORK ITEM, not off the assignment or the occurrence.** The line is
   what carries an agreed price, `work_items.contract_version_id` is NOT NULL and foreign-keyed, and
   «the price on the published baseline» is a statement about the line.
6. **A cause row with no money keeps its drill-down.** A code that lost the precedence holds no
   assignment and no amount, and dropping its row would delete the only route from «this obligation
   is unmet» to the screen. `assignmentCount` may therefore be `0`; `requirementOccurrenceIds` may
   not be empty, and the schema says `.min(1)`.
7. **`liveBlockedReasons` was EXTRACTED rather than copied.** M6 sums exactly the list M3 renders. A
   filter written twice is a total that stops equalling the list beneath it the first time one copy
   is edited, so `blocked_reasons.get` now calls the same function and the suite asserts the two
   payloads' `blockedReasons` are **equal**, not merely similar.
8. **ADR-008's bucket is named `performed_not_admitted`.** The ADR says the projection «owes it a
   bucket» and does not name one; the name is fixed here, in the shape of the two states the ADR
   distinguishes it from (`evidence_blocked`, `ready_not_packaged`). `state-catalog.csv` has no
   machine for it and `value-at-risk.md` has no row — **both recorded as owed rather than edited by
   this slice**, because the seven-state projection they would join is v0.2 and a v0.1 read may not
   write v0.2 vocabulary into a level-2 document. The glossary gained the term, which is the term
   authority and not the projection.
9. **The bucket's money is computed by `sliceAllocation` — the allocator itself.** The figure means
   «what admission would carve for this quantity if it happened now», and the only way to make that
   sentence true rather than approximately true is to call the function the closure calls, against
   the state it would read: already-admitted quantity as `workItemPerformed`, already-taken minor
   units as `workItemAllocated`. A second proportional formula would drift the first time the
   coupling rules or the largest-remainder tie-break changed, invisibly, because both sides would
   still look reasonable.
10. **The bucket OVERLAPS blocked value and says so.** A blocked stage's quantity is both unadmitted
    and blocked. `isSummandOfBlockedValue: false` is a wire literal. The overlap is the point: «nobody
    has tried to close the stage» and «somebody tried and was refused» are different operational facts
    about the same money, and a screen showing only the second would report a pilot as unblocked on
    the day nobody used it.
11. **«Admitted» is `exists(valuation_allocations)`, and the v0.1 final review found that this is a
    proxy after all.** After ADR-008 `progress.record` writes no allocation, `progress.adjust`
    writes one only against an already-admitted root, and `admitClosedStageQuantity` is the only
    other writer. The same predicate with the sign flipped is `appendValuationAllocation`'s
    `work_item_performed`, and the two are deliberately the same shape so «waiting» and «already
    competing for the pool» partition the line's entries exactly.
    **Recorded 2026-08-08 — this item overstated the guard and the overstatement is load-bearing.**
    The gate the adjustment route applies asks «does this lineage hold money», not «was this
    quantity admitted», so **one** legitimate admission opens the door permanently for that root:
    record 0.000001, close a stage honestly, then `progress.adjust +9.999999` on the same root and
    the correction carves with `admitted_by_closure_id` NULL and takes what is left of the pool. It
    needs `progress.adjust` — a foreman — and no second closure. `blocked_value.get` would **not**
    show it, because after the carve the adjustment holds an allocation and therefore reads as
    admitted, which is this item's own predicate answering wrongly. It is the v0.1 final review's
    CRITICAL finding, it is **not fixed**, and it is filed in §5 as item 63 with the exact fix.
12. **A negative unadmitted total THROWS.** It would mean a lineage whose corrections outweigh its
    root while none of it is admitted, which `progress.adjust` refuses at 422. Rendering
    `-3.000000` as money waiting would be worse than failing.
13. **Over-contract is the allocator's own shortfall.** `sliceAllocation` returns `fundedQuantity`;
    the rest performed and drew nothing (INV-039). Deriving the over-contract part from that answer
    means the bucket and the allocator can never disagree about where the contract boundary is. The
    register is reported by **quantity only** and its row has no money field at all — enumerated by
    key in both suites, because a later `netMinorUnits: "0"` there is exactly the INV-038 regression.
14. **Zero price is INSIDE the sum; missing price is not.** «Zero price receives a known monetary
    value of zero; it participates in reconciliation and state counts.» So a zero-priced assignment
