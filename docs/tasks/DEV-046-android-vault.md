## What is not true after this task

Nothing here is observed on a physical Android device: hardware Keystore level, OEM behaviour, real backup and device-to-device transfer, low-memory 32-bit phones, a real 16 KB device, camera HAL output and Play Internal install all stay NOT RUN (BL-002).

- No camera capture and no real upload ran on Android. Import, identity switch, quarantine, restore, discard and an upload to an unreachable local origin ran over the debugger with test UUIDs and no server (rows 7, 8); receipt confirmation did not.
- Only arm64-v8a ran. armeabi-v7a is built and linked but never executed; x86 and x86_64 are no longer shipped (owner decision).
- On Android 10–14 the keys are usable while the phone is locked after an earlier unlock (row 7, S12).
- `allowBackup=false` stops cloud backup; on Android 12+ device-to-device transfer may still copy the app's shared preferences that expo-secure-store's `dataExtractionRules` do not exclude (not SecureStore itself). The vault is never copied: it lives in `no_backup`, outside the `sharedpref` domain, and its Keystore keys cannot leave the device (S13, F3).
- A Keystore failure that persists across starts while a `server_confirmed`, `discarded` or `importing` row exists makes `openJournal` fail and the whole vault unavailable until the Keystore recovers. iOS has the same behaviour (`NativeVault.swift` start-up clean-up); accepted as parity (F1).
- R9: after the 185 s deadline the transfer slot is released only when the writer returns; a `disconnect()` that never unblocks it would leave uploads `VAULT_UPLOAD_BUSY` until restart (not observed; deferred).
- With the process-wide vault (S16), an old module's `OnDestroy { cancel(true) }` during a development JS reload reaches the shared vault; if it ran after the new JS authenticated it would close the identity once (one re-authentication). Development builds only; not tested.
- The iOS libsodium build uses the same `CFLAGS` without `-ffile-prefix-map`, so the iOS xcframework likely embeds the builder's paths too; not checked, out of this task's scope.
- Key deletion, the `VAULT_KEYSTORE_UNAVAILABLE` branch of `cleanup`, the checkpoint and a Keystore that throws for a missing alias were not exercised.
- Keys and plaintext chunks pass through the Java heap on Android (the iOS vault keeps them native); `fill(0)` cannot reach copies a moving GC made.
- A React warning at JS startup («Can't perform a React state update on a component that hasn't mounted yet») appeared in Metro's log; the JS is unchanged here and it was not investigated.

## Sources

- expo-modules-core 57.0.18 (installed): `runOnQueue(CoroutineScope)` in `BaseAsyncFunctionComponent.kt`, and its `android/build.gradle` passing `-DANDROID_SUPPORT_FLEXIBLE_PAGE_SIZES=ON`; read in `node_modules` 2026-09-24.
- Android Developers, «Support 16 KB page sizes», https://developer.android.com/guide/practices/page-sizes (last updated 2026-09-16, accessed 2026-09-24): NDK r27 link flags `-Wl,-z,max-page-size=16384` and `-Wl,-z,common-page-size=16384`; verification with `zipalign -c -P 16 -v 4` and `llvm-objdump -p … | grep LOAD`. The page does not mention `ANDROID_SUPPORT_FLEXIBLE_PAGE_SIZES`; that flag follows expo-modules-core.
- Java Native Interface Specification (Java SE 17), «Design Overview — Exception Handling», https://docs.oracle.com/en/java/javase/17/docs/specs/jni/design.html (accessed 2026-09-24): with an exception pending only a listed set of functions may be called, `ReleaseStringUTFChars` among them, `FindClass` and `ThrowNew` not.
- Android API reference, `android.system.OsConstants` (API 36 on the emulator): no `O_DIRECTORY` constant — observed as a Kotlin compile error, not re-read.
- Metro in React Native 0.86.3 (installed): the inspector proxy refuses DevTools connections without a localhost `Origin` — observed in Metro's log 2026-09-24.

- Android Developers, `KeyGenParameterSpec.Builder#setUnlockedDeviceRequired`, https://developer.android.com/reference/android/security/keystore/KeyGenParameterSpec.Builder (last updated 2026-08-03, accessed 2026-09-24): added in API 28; Android 12–14 cannot create or use such keys without a secure lock screen and delete them when it is removed; «use setUnlockedDeviceRequired(true) only on Android 15 and higher».
- Android Developers, «Behavior changes: Apps targeting Android 12», https://developer.android.com/about/versions/12/behavior-changes-12#backup-restore (last updated 2026-09-16, accessed 2026-09-24): on some manufacturers' devices `allowBackup="false"` disables Google Drive backup but not D2D transfer; `dataExtractionRules` controls D2D.
- `@expo/config-types` 57.0.2 (installed): `android.allowBackup` (its description, «no backup or restore … will ever be performed», overstates the Android 12+ behaviour above); `expo-build-properties` 57.0.21 (installed): `android.buildArchs` written to `reactNativeArchitectures`.
